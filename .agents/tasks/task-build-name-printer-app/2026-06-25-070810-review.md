# Serverless name-printer: frontend, Lambda, and CDK wiring

A complete greenfield implementation of a form-submit app: static frontend served via CloudFront/S3, a Lambda behind API Gateway that returns a greeting, and a CDK stack that wires everything together. The infrastructure rewrite replaces broken CDK v1-style patterns (inline Lambda code, nonexistent `add_object_from_asset`, manual OAC construction) with idiomatic CDK v2 constructs. The frontend is a single-page form with client-side validation and fetch-based submission.

**Watch for:** The `API_ENDPOINT` placeholder in `script.js` is a literal string `"API_ENDPOINT"` — the app will fail at runtime unless a deployment step substitutes the actual API Gateway URL (confirmed). The Lambda handler does not cap input length, allowing arbitrarily large `name` values through to the response (confirmed). CORS is configured as `allow_origins=["*"]` on both API Gateway and Lambda response headers with no further restriction (confirmed).

## High-level view

The CDK stack is structurally sound with idiomatic CDK v2 constructs, but the deployment pipeline has a gap: nothing injects the API Gateway URL into the frontend JavaScript. The hardcoded `"API_ENDPOINT"` placeholder will cause every form submission to fail against a real deployment.

The Lambda does not validate input length or sanitize the name before echoing it back, which is low-risk for a greeting app but worth noting if the response is ever rendered as HTML rather than `textContent`.

The frontend has no loading state during the async fetch, so rapid double-submits or slow networks produce no user feedback.

## API endpoint injection gap

The frontend's `script.js` opens with `const API_ENDPOINT = "API_ENDPOINT";` — a raw string literal, not an environment variable or template token. The CDK stack outputs `ApiURL` as a `CfnOutput` but nothing connects that output to the deployed static assets. Every form submission will fire a fetch to `API_ENDPOINT/submit`, which will fail with a network error caught by the generic catch block.

The typical fix is either (a) a post-deployment step that rewrites the JS file in the S3 bucket using the stack output, (b) a small `config.js` generated by a CDK custom resource and loaded by the HTML, or (c) a build-time substitution if there's a CI pipeline. None of these are present.

## Input validation and response echo

The Lambda validates presence (`not name` after `.strip()`) but not length. A POST body with a megabyte-long `name` value will be parsed, echoed back in the JSON response, and stored in CloudWatch logs. If the app ever gains persistence or the response is rendered outside `textContent`, unbounded echo becomes a vector.

## CORS posture

Both the API Gateway `default_cors_preflight_options` and the Lambda response headers specify `Allow-Origin: *`. They're consistent with each other, but for anything beyond a public demo the origin should be restricted to the CloudFront distribution domain.

## Frontend UX gap

There is no loading indicator or button-disabled state during the async fetch. On slow connections the user sees no feedback between clicking Submit and receiving the greeting or error. Rapid clicks will fire multiple requests. A `button.disabled = true` during the await would cost one line and eliminate the issue.
